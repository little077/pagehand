# v0.3 UI 迭代 · 运行块：把一串工具调用收成一张可折叠的过程卡

> 迭代日期：2026-11-17
> 状态：代码、22 个单测、380px 渲染验收完成；真实扩展 + 真实模型链路待验收

## 1. 本次迭代做了什么

把「每个工具调用一张平铺卡片」改成「一次运行一个可折叠的运行块」：

- 默认折叠。头部实时显示当前在做什么、已执行几步、耗时。
- 运行中提供停止按钮；失败自动展开；用户可随时点开看步骤。
- 展开后每一步只显示动作、摘要、耗时和状态；点某一步再打开底部弹层看参数和结果。
- 最终回答单独成气泡，不再和过程混在一起。
- 助手头像从写死的 `PH` 换成用户提供的机器人图片。

| 类型 | 文件 | 说明 |
| --- | --- | --- |
| 分组与状态 | `entrypoints/sidepanel/lib/runs.ts` | 按用户消息切 Run、识别回答/过程说明、推导运行状态与头部文案 |
| 运行块 | `entrypoints/sidepanel/components/AgentRun.tsx` | 折叠头部、实时动作、计时、停止、步骤列表；步骤详情在行下原地展开 |
| 回答气泡 | `entrypoints/sidepanel/components/AssistantBubble.tsx` | 复用 Markdown 渲染，头像换成品牌图片 |
| 列表接线 | `entrypoints/sidepanel/components/MessageList.tsx` | 从「逐条工具卡」改为「逐块运行」 |
| 删除旧卡片 | `entrypoints/sidepanel/components/ToolCard.tsx` | 由运行块里的步骤行取代，避免两套过程 UI |
| 停止操作 | `entrypoints/sidepanel/App.tsx` | 把 `busy` 与 `onStop` 传给消息列表 |
| 头像资源 | `public/pagehand-avatar.png` | 用户提供的图片裁成 128×128、29KB |
| 测试 | `tests/sidepanel/runs/` | 分组 / 状态文案 / 用户场景三类 |

## 2. 为什么改

真实截图里一次任务连续调用了 7 次工具，旧 UI 渲染成 7 张带编号和连接线的卡片，像一架梯子：

- 用户先看到的是过程噪音，最后才看到答案；
- 每张卡片都占一段垂直空间，侧栏很快被工具卡淹没；
- 没有「一次运行」的概念，无法回答「这一轮跑到哪了、花了多久」。

行业里比较稳定的做法是把过程收进 Run：默认折叠、头部给状态、展开给细节、结果单独展示。本次按这个方向落地。

## 3. 技术方案与选型

### 3.1 不新增协议，前端派生

分组完全基于现有 `ChatItem[]` 推导，不改后台协议、不迁移历史数据：

- 一条用户消息到下一条用户消息之间的所有非交互项，归为一个 `RunView`。
- 交互卡片（提问 / 授权）不参与分组，继续由 `PendingDeck` 独立浮层展示。
- 历史会话恢复后同样走这套分组，不需要额外字段。

### 3.2 Run 的字段

| 字段 | 用途 |
| --- | --- |
| `tools` / `stepCount` | 运行块里的工具步骤与数量 |
| `notes` | 工具之间出现的模型文字，作为「过程说明」收在展开区 |
| `answer` | 最后一次回答，单独渲染成气泡 |
| `status` | `running` / `done` / `error` / `stopped` |
| `currentTool` | 正在执行的工具，用于头部「正在检查页面元素…」 |
| `startedAt` / `endedAt` / `elapsedMs` | 头部计时与完成态耗时 |

### 3.3 状态推导

- 有工具在跑且本轮 `busy`：运行中；
- 有工具在跑但 `busy` 已结束：已停止（用于用户点停止后工具没有正常收尾）；
- 任一工具失败或回答失败：失败，并指出第几步；
- 回答正在流式输出或本轮仍在 `busy`：运行中；
- 其余：完成。

`busy` 是全局状态，因此只有最后一个 Run 会被判为运行中，旧 Run 不会因为当前任务还在跑而显示转圈。

### 3.4 前端表现

- 折叠头部：状态图标 + 文案 + 运行中耗时 + 停止按钮 + 展开箭头。
- 头部文案（工具折叠统一带「工具」，为后续独立思考折叠留出区分）：
  - `思考中…`（还没调用工具；后续由独立思考块接管）
  - `正在执行工具（3/7）：检查页面元素…`
  - `已执行 3 个工具 · 正在整理回答…`
  - `已执行 3 个工具 · 等待下一步…`
  - `已执行 7 个工具 · 3 秒`
  - `工具执行失败 · 第 2 步`
  - `工具执行完成 · 回答生成失败`
  - `工具执行已停止 · 3 个`
- 展开区：过程说明 + 步骤行（编号、图标、动作、摘要、耗时、状态）。
- 点击步骤：在该步骤下方**原地展开**参数与结果 JSON，一次只展开一个；再点一次收起。不使用底部弹层。
- 失败：自动展开，避免用户以为只是慢。
- 纯问答（没有工具调用）：不渲染运行块，保持普通聊天气泡。
- 用户刚发出任务、模型还没返回：渲染一个空的「思考中…」块，提供停止入口。

### 3.5 头像

用户提供 `金色能量环绕的未来机器人.png`，原图 1254×1254、1.7MB。裁成 128×128、29KB 的 PNG，放在 `public/pagehand-avatar.png`，回答气泡以 24px 圆角方块展示。

### 3.6 折叠层级：按任务，不按工具

稳定的层级是 **Conversation > Run > Step > Detail**：

- 一次用户请求是一个 Run，里面连续 N 次工具调用是逐条 Step；
- Run 默认折叠，头部回答「这次任务跑到哪」；
- 点开 Run 看到步骤列表，点某一步才在行下展开「这次调用干了什么」；
- 不按每个工具一个顶层折叠：10 次顺序调用会变成 10 个折叠，用户要先逐个展开才能拼出任务全貌，也最容易退化成原来的「梯子」。

只有存在明确计划阶段或并行分支时，才在 Run 内部再按阶段分组，而不是按工具调用分组。当前 Pagehand 没有规划器，Run 级分组已经够用。

## 4. 用户场景

1. **多步查找**：用户问「输入框在哪」，Agent 调了 7 次工具。现在只出现一张「已完成 · 7 步」的折叠块，答案在下方；需要复盘时再展开。
2. **中途失败**：第 3 步失败时头部直接写「第 3 步失败」并自动展开，用户知道卡在哪，而不是只看到「完成」。
3. **中途停止**：运行中头部有停止按钮；点停止后显示「已停止 · N 步」，不会一直转圈。
4. **纯问答**：用户说「你好」，不出现运行块，保持简单对话的节奏。
5. **查看某一步细节**：点开运行块，再点「检查页面元素」，参数和结果直接在该步骤下方展开，不跳到底部弹层，也不把 JSON 堆进对话流。

## 7. 已知边界

- 没有做「真实思考内容」：本轮只显示运行状态。模型 thinking 事件目前没有转发，后续单独一期处理。
- 用户手动展开的 Run 在完成后不会自动收起，尊重用户当下的选择；默认状态始终是折叠。
- 如果用户停止时最后一个工具已经正常结束、但模型还没来得及回答，状态会显示「已完成」而不是「已停止」，因为现有数据里没有明确的取消标记。
- 回答里的工具名、编号、内部字段仍可能被模型说出来，这是提示词输出规范问题，另行处理。
- 运行块只在 UI 层派生，没有把分组写回会话记录；跨端/导出如果将来需要 Run 结构，需要再补持久化字段。
