# v0.5 技术方案 · 输入框图片节点：粘贴、拖拽、悬停放大

> 日期：2026-11-18
> 状态：**已实施**；380px 粘贴 / 拖拽 / 悬停 / 发送已实测，真机扩展加载与系统剪贴板待验收
> 目标版本：v0.5
> 前置能力：v0.4 输入框截屏附件 + IndexedDB v2（本迭代同时升到 v3）
> 约束：不复制任何 AGPL 项目代码；UI 遵守 `docs/ui-guidelines.md`；会话读写只在后台

## 1. 结论

**可行，推荐做，但“异步上传到 IndexedDB”这一步要改定义。**

- 粘贴 / 拖拽拿到的是 `File`，没有本地路径，用 `URL.createObjectURL(file)` 做即时预览，符合预期；
- 图片用**自定义 Tiptap Node**（`inline atom`）实现，不引入 `@tiptap/extension-image`；
- 节点 `attrs.status` 驱动 UI：`preparing → ready / error`；
- NodeView 用 `NodeViewWrapper` 包住，内部 `contentEditable={false}`；
- 必须同时实现 `parseHTML` + `renderHTML`，否则复制、导出、撤销恢复会丢图；
- 异步完成时按 `draftId` 在文档里找节点，找不到就静默返回（用户已删除）；
- **输入阶段不直接写 IndexedDB**：当前库是“会话归属 + 会话写入时清理”的模型，未发送图片还没有会话 id，提前写会产生孤儿数据，也会违反“会话读写只在后台”的工程约束。异步阶段只做本地编码/测量/哈希，点发送时沿用现有链路一次性落盘；
- 悬停放大用一个共享的浮层做**双层交叉淡入淡出**，在多张缩略图之间移动时不会闪断；
- 发送链路 `send.images`、会话存储、消息气泡渲染**都不需要改**。

需要拍板的 4 件事在最后一节，本文默认按推荐项设计。

## 2. 现状核对

### 2.1 输入框

`entrypoints/sidepanel/components/Composer.tsx`：

- Tiptap 3.31.4 纯文本编辑器；工具栏和附件托盘都在 `EditorContent` 外面；
- 图片当前是 **React state**（`attachments`）里的 `ImageAttachment[]`，不是编辑器节点；
- 唯一入口是「截屏」按钮，结果是 `CaptureResult.image`；
- 限制：最多 3 张、单张 2 MB、总计 4 MB；
- `supportsImages=false` 时按钮禁用，已有附件也发不出去；
- 发送时 `editor.getText()` 取文字，`attachments` 原样交给 `onSend`。

### 2.2 会话与图片存到哪里

| 位置 | 内容 |
| --- | --- |
| IndexedDB `pagehand-sessions` v2 | `sessions`：会话记录（`items` + 模型 `messages`） |
| 同上 | `attachments`：`{ id, sessionId, mimeType, size, data(base64), createdAt }`，`sessionId` 建索引 |
| 同上 | `sessionMeta`：会话列表摘要 |
| `chrome.storage.local` | 当前会话 id，key `pagehand.sessions.current.v1` |

写入时机（`lib/agent/session.ts`）：

1. 用户第一次发送前没有 `sessionId`，**发送时**才 `crypto.randomUUID()`；
2. 一轮结束（或工具结束/交互卡落盘）才 `schedulePersist()`；
3. `writeSession()` → `dehydrateSession()` 把 `items` / `messages` 里的 base64 抽到 `attachments`；
4. 图片 id 是 `mimeType + base64` 的 SHA-256，同图只存一份；
5. `items` / `messages` 只留 `attachmentId` 引用，读取时再还原；
6. 每次 `writeSession` 会删掉该会话不再引用的附件；`removeSession` 清理整会话附件。

另外 `AGENTS.md` §2 明确：**会话读写只在后台进行，UI 不直接读 IndexedDB**。

### 2.3 结论：输入阶段能不能写库

| 方案 | 能不能 | 问题 |
| --- | --- | --- |
| 粘贴时直接在侧边栏写 `attachments` | 技术上能 | 违反“只在后台读写”的边界；图片没有真实 `sessionId`；`writeSession` 的清理逻辑会把未发送的草稿当孤儿删掉；侧栏关闭后留下无人认领的数据 |
| 走 Port 让后台写草稿 | 能 | 要新增协议、DB v3 草稿区、TTL 清理、关闭恢复策略，改动量翻倍 |
| **只做异步编码，发送时落盘（推荐）** | 能 | 关闭侧栏会丢未发送草稿；但和现在“未发送文字也会丢”的行为一致 |

**推荐第三条。** “先插节点、异步处理”保留，只是异步内容从“上传数据库”改成“读取文件 → base64 → 尺寸 → 哈希”，这些都在内存完成，状态可见。真正落盘仍由现有 `send → session → writeSession` 完成，存储零改动。

## 3. 最终交互

```
┌─────────────────────────────────────────────┐
│  截屏                              ● 视觉模型 │
├─────────────────────────────────────────────┤
│  [缩略图1] [缩略图2] 问问这一页…             │  ← 图片节点在编辑器内
│                                             │
├─────────────────────────────────────────────┤
│  Enter 发送 · Shift + Enter 换行    2/3  ↑  │
└─────────────────────────────────────────────┘

悬停某张缩略图：

        ┌───────────────┐
        │               │  220×220 方形浮层
        │    放大图片    │  深色底、圆角、阴影
        │               │  右下角标 1024×768
        └───────────────┘
             ▲
          [缩略图]
```

- 粘贴：截图工具复制后 `Ctrl+V`，或网页里复制图片；
- 拖拽：从文件管理器/桌面把图片拖进输入框；
- 插入位置：当前光标处；拖拽按落点位置；
- 缩略图沿用现有托盘的视觉：约 86×48、圆角、边框、右上角删除；
- 悬停：浮层在缩略图上方，鼠标在多张缩略图间移动时旧图淡出、新图淡入（约 180ms，轻微缩放），不闪断；
- 删除：缩略图右上角 `×`；
- 发送：图片和文字一起走现有 `send.images`；用户气泡样式不变；
- 纯文本模型：粘贴/拖拽直接拒绝并提示，原因和现在「截屏」禁用一致。

## 4. 自定义 Node

### 4.1 Schema

```ts
ImageNode = Node.create({
  name: 'pagehandImage',
  group: 'inline',
  inline: true,
  atom: true,        // 无子内容；isEmpty 会把 atom 视为非空
  draggable: true,
  selectable: true,
  addAttributes() {
    return {
      draftId: {},        // 本次插入的唯一 id，异步回填的定位键
      attachmentId: {},   // 内容哈希；ready 后才有
      src: {},            // preparing: blob:；ready: data:image/...
      mimeType: {},
      size: {},
      width: {},
      height: {},
      name: {},
      status: {},         // 'preparing' | 'ready' | 'error'
      error: {},
    };
  },
  parseHTML() {
    return [{ tag: 'img[data-pagehand-image]' }];
  },
  renderHTML({ HTMLAttributes }) {
    return ['img', { ...HTMLAttributes, 'data-pagehand-image': 'true' }];
  },
  addNodeView() {
    return ReactNodeViewRenderer(ImageNodeView);
  },
});
```

要点：

- `inline atom` 与原生 Image 扩展的定位一致，粘贴在文字中间也能落在光标处；发送时图片和文字本来就是两个数组，不依赖文档顺序；
- `draftId` 必须进 attrs，异步回调不能依赖 `getPos()`（用户可能已经删除或撤销）；
- `src` 在 preparing 阶段是 blob URL，ready 后换成 data URL：这样 `renderHTML` 永远有可用地址，复制/导出/撤销恢复不会拿到失效的 blob；
- 不用 `data-pagehand-ref` 之类的全局编号，避免和 inspect 的 ref 体系混淆。

### 4.2 NodeView 硬约束

```tsx
<NodeViewWrapper
  as="span"
  contentEditable={false}
  data-drag-handle
  className="..."
>
  <img ... />
  <button ... />
</NodeViewWrapper>
```

- 必须用 `NodeViewWrapper`，否则 React NodeView 的 DOM 归属和 ProseMirror 事件会乱；
- 内部 `contentEditable={false}`，防止光标进入图片节点、输入被吞；
- 删除按钮 `onMouseDown={(e) => e.preventDefault()}`，避免点击时先产生选区；
- `deleteNode()` 优先用 NodeView props；异步回填用文档遍历，不用 NodeView 的旧 props；
- 节点被选中时给 `selected` 样式环；
- 拖拽排序依赖 `draggable` + `data-drag-handle`。

### 4.3 为什么 renderHTML 不能省

- Tiptap 的复制、粘贴、撤销、`editor.getHTML()` 都走 `renderHTML`；只写 NodeView 的 React 组件，文档序列化时这个节点会被当成空内容；
- `parseHTML` 负责把复制的 `<img data-pagehand-image …>` 重新变回自定义节点；
- 只接受带 `data-pagehand-image` 的图片，或 `data:image/*` 的 `src`；不加载远端 `http(s)` 图片，避免复制网页时产生外部请求和隐私泄露；
- preparing 阶段复制出去可能是 blob URL，跨应用不可用；ready 后是 data URL，可正常粘贴到别处。

## 5. 粘贴与拖拽

### 5.1 拦截位置

用 Tiptap `editorProps.handlePaste` / `handleDrop`（ProseMirror 层），不要只在 wrapper 上监听 `onPaste`：

- `handlePaste(view, event)`：
  - 从 `clipboardData.files` 和 `clipboardData.items` 里收集 `image/*` 文件；
  - 没有图片 → `return false`，保持正常文本粘贴；
  - 有图片 → `preventDefault()`，在 `view.state.selection` 处插入节点；
  - 图文混合：先插入图片节点，再把 `text/plain` 插到图片后面（不能直接吞掉文字）。
- `handleDrop(view, event, _slice, moved)`：
  - `moved === true` 是编辑器内部拖动排序，`return false`；
  - `dataTransfer.files` 有图片 → 用 `view.posAtCoords({ left, top })` 算落点，插入；
  - 其余情况交给默认行为。
- 输入框外层再兜一个 drop（P1，可选）：拖到工具栏等非编辑区时插到文末，并给整个 composer 加拖拽高亮；必须防止和编辑器内 drop 重复插入。

### 5.2 插入前校验

复用现有限制，并在插入前判：

| 规则 | 行为 |
| --- | --- |
| 当前模型不支持图片 | 拒绝，提示切模型 |
| 现有图片 + 新文件 > 3 张 | 只插到 3 张，多余提示 |
| 单张 > 2 MB | 先降采样；仍超限则拒绝 |
| 总计 > 4 MB | 拒绝新文件 |
| 非 `png/jpeg/webp/gif` | 拒绝；**不允许 SVG**（可带脚本） |
| 同一内容重复粘贴 | 可选：按哈希去重，提示“已在输入框里” |

粘贴的截图常见 1920×1080 PNG，原图很可能超过 2 MB。建议：超过 2 MB 时在侧边栏 Canvas 按最长边 1600、JPEG 0.8 重编码，和现有截屏路径保持同一上限；重编码后仍超限才拒绝。

### 5.3 异步处理流程

```text
paste/drop
  → 校验数量/大小/类型
  → URL.createObjectURL(file)          // 立即有预览
  → 光标处插入节点 status=preparing
  → 异步：arrayBuffer → base64
          createImageBitmap → 宽高
          attachmentIdFor(mime, base64) // 现有 SHA-256 工具
  → 按 draftId 找到节点，setNodeMarkup：
       status=ready, src=data URL, attachmentId, width, height, size
  → 找不到节点：静默返回（用户删了/撤销了）
  → 失败：status=error + error 文案，保留预览
```

- 每张图独立异步，互不阻塞；
- 所有完成回调都通过 `draftId` 定位，不持有 `getPos()` 结果；
- `draftId → { file, blobUrl, canceled }` 存 `Map`，编辑器销毁时统一 revoke；
- 删除节点不需要 cancel 网络请求（没有网络），只是标记取消，回调静默；
- 不用 FileReader 的回调形式，统一 `await file.arrayBuffer()`，异常路径更清楚。

### 5.4 撤销/重做风险

`setNodeMarkup` 更新 attrs 也会进 ProseMirror 历史：

- 用户先撤销到 `preparing`，再重做回 `ready`：字符串相同，没问题；
- 用户先撤销到 `preparing`，之后历史被截断：节点永远停在转圈；
- 缓解：保留 `draftId → 最终 attrs` 的结果表；NodeView 挂载/更新时如果看到 `preparing` 且结果表里有值，再补一次 `setNodeMarkup`。这是幂等操作，成本很低。

## 6. 悬停放大与过渡

### 6.1 结构

浮层放在 **Composer 内部、EditorContent 外面**，`position: fixed`：

```
ImageHoverPreview
  ├─ layer A（旧图）opacity 1 → 0
  └─ layer B（新图）opacity 0 → 1
```

- 尺寸 220×220，`object-contain`，深色底 + 圆角 + 阴影；
- 位置由缩略图 `getBoundingClientRect()` 计算，优先在上方；越界时翻到下方，水平方向夹在 380px 侧栏内；
- `pointer-events: none`，`aria-hidden`，不抢鼠标；
- 显示尺寸、`preparing` 时显示“处理中”。

### 6.2 多图之间切换

- 悬停 A → 显示 A（A 在下层，直接可见）；
- 悬停 B → A 留在下层并淡出，B 在上层淡入，180ms；
- 鼠标离开缩略图后延迟约 80ms 再隐藏，移动到下一张时取消隐藏，避免闪断；
- 过渡用 `opacity` + `scale(0.98 → 1)`，`will-change: opacity, transform`；
- `prefers-reduced-motion: reduce` 时去掉过渡，直接切换；
- 滚动/窗口尺寸变化时重新计算位置，缩略图移出视口就隐藏。

跨 NodeView 共享状态有两种接法：

1. React Context 包住 `EditorContent`（portal 保留 context）；
2. 扩展 options 里传一个稳定的 ref 对象，NodeView 通过 `extension.options.previewApi.current` 调 `show/hide`。

推荐 Context，更符合现有 React 结构；若实测 NodeView 拿不到 Context，再退到 ref 方案。

## 7. 发送

`Composer` 里新增两个纯函数（便于测试）：

```ts
collectImageAttachments(doc): ImageAttachment[]  // 按文档顺序，只收 status=ready
collectImageStats(doc): { count, preparing, error }
```

发送流程：

1. 有 `preparing` → 禁止发送，按钮禁用，提示“图片处理中…”；
2. 有 `error` → 禁止发送，提示移除或重试；
3. 文字仍用 `getText()`；atom 节点没有文本，不会污染提示词；
4. `ImageAttachment` 从节点 attrs 还原（`src` 去掉 `data:<mime>;base64,` 前缀）；
5. `onSend(text, images)`；
6. 成功后 `clearContent`，清空草稿表和 blob URL（此时后台已拿到 base64 副本）；
7. 纯文本模型在插入阶段就拒绝，发送阶段保留现有兜底。

发送后的链路完全不变：

`Composer → send.images → AgentSession.send() → agent.prompt(text, images) → writeSession() → attachments store`

用户气泡继续用 `ChatItem.user.attachments` 渲染 data URL，样式不动。

### 7.1 对现有代码的一个必要修正

现在 `canSend` 依赖 `attachments.length`。改成节点后：

- `hasImages = collectImageStats(doc).count > 0`；
- `canSend = (text 非空 || hasImages) && !busy && !capturing && (hasImages ? supportsImages : true) && preparing === 0 && error === 0`；
- `editor.isEmpty` 不会把 atom 当空（`isAtom || isLeaf` 直接返回 false），所以仅图片时占位符会正常消失；
- 但 `getText()` 对 atom 没输出，不能用文字长度判断有没有图片。

## 8. 截屏入口怎么处理

- 现有「截屏」结果 `ImageAttachment` 已经有 base64，直接以 `status=ready` 插入节点；
- 删除输入框上方的附件托盘和 `attachments` state；
- 截屏的限制、模型能力门禁、绿色激活态、提示条全部保留；
- 这样“截屏 / 粘贴 / 拖拽”三条入口共用同一个节点和发送逻辑。

## 10. 影响与风险

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| 编辑器从纯文本变成含原子节点 | Enter 发送、光标移动、删除、全选行为可能变化 | 用 `inline atom` + `contentEditable=false`；手测 Backspace/Delete/全选/Shift+Enter |
| `getText()` 拿不到图片 | 图片-only 消息被误判为空 | 用 `collectImageStats(doc)` 判断，不依赖文字 |
| 撤销/重做回退 status | 缩略图停在转圈 | 结果表 + 挂载时幂等回填 |
| blob URL 生命周期 | 撤销恢复后预览失效/内存泄漏 | 编辑器生命周期内保留，销毁时统一 revoke；ready 后 src 换 data URL |
| 大图内存 | 3 张 2 MB 的 base64 + blob 约 5–8 MB | 限制总量；必要时降采样；发送后清空 |
| 复制到外部应用 | preparing 阶段的 blob URL 不可用 | 只有 ready 的 data URL 保证可复制；文档写明 |
| 粘贴图文混合 | 图片插入后文字被吞 | 先插图片，再补插 `text/plain` |
| 内部拖动排序被当成新粘贴 | 图片重复 | `handleDrop` 里 `moved === true` 直接放行 |
| 远端图片自动加载 | 隐私/追踪 | `parseHTML` 不接受 `http(s)` 图片 |
| SVG 脚本风险 | 安全 | MIME 白名单排除 SVG |
| 输入阶段不落库 | 关闭侧栏丢未发送图片 | 与现有未发送文字一致；若要草稿持久化，单独立项 DB v3 |

## 13.2 附件跨会话归属修复（IndexedDB v3）

问题：`attachments` 以内容哈希为主键、每条记录只带一个 `sessionId`；同一张图出现在两个会话时，后写的会话会覆盖归属，先写的会话再读会丢图。

修复：

- `attachments` 只存图片本体，按内容哈希全局去重，不再带 `sessionId`；
- 新增 `sessionAttachments` 关联表：`{ key, sessionId, attachmentId }`，`sessionId` / `attachmentId` 各建索引；
- 写入会话时重建该会话的关联，只有没有任何会话再引用的附件才删除本体；
- 删除会话时先删关联，再按引用计数清理附件；
- 读取会话先查关联表，再按 `attachmentId` 取图片；
- DB 升到 v3：升级时扫描已有会话记录，用其中的 `attachmentId` 回填关联表。历史 v2 里同一张图被两个会话引用的情况也能恢复；
- 测试：同一张图写入两个会话，两边都能读出；删除一个会话另一个不受影响；最后一个会话删除后附件本体清空；另加 v2→v3 迁移测试。
