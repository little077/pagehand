## 1. 本次迭代做了什么

新增一个只读工具 `inspect`，让 Agent 知道当前页面上有哪些能操作的按钮、链接、输入框、下拉框、复选框和可编辑区域。每个元素返回编号、类型、名称、当前值、可见性、是否被遮挡。

具体改动：

| 类型 | 文件 | 说明 |
| --- | --- | --- |
| 页面侧采集器 | `lib/page/inspect.ts` | 注入到页面执行的只读函数，产出结构化快照 |
| 工具定义 | `lib/tools/inspect.ts` | 参数校验、标签页解析、注入与错误处理 |
| 模型格式与 UI 详情 | `lib/tools/inspect-format.ts` | 把快照转成模型可读文本，并生成给 UI 的摘要 |
| 工具注册 | `lib/tools/index.ts` | 加入白名单与工具数组 |
| 系统提示 | `lib/agent/prompt.ts` | 告诉模型何时用、怎么引用编号、密码框不出现 |
| 步骤摘要 | `lib/agent/session.ts` | 时间线显示「找到 N 个可操作元素 · M 个不可见」 |
| 前端标签与图标 | `entrypoints/sidepanel/components/ToolCard.tsx` | 「检查页面元素」 + 鼠标指针图标 |
| 测试 | `tests/tools/inspect/` | 4 类、33 个用例 |

**本次不做**：点击、填写、滚动、跨标签页检查、iframe 深层遍历、Shadow DOM 穿透、写操作权限门禁。这些留给后续版本。

## 2. 为什么先做它

阶段 4 的写操作不能凭空开始。模型要点击或填写，必须先回答三个问题：

1. 页面上有哪些可操作元素？
2. 哪个元素是用户说的那一个？怎么稳定指代它？
3. 为什么某个元素点不到？

`read_page` 回答不了这三个问题——它读的是正文，不是控件；截图也给不了可定位的标识。所以 `inspect` 是写操作的第一块地基，也是当前版本唯一能安全交付的增量：它只读，不改变页面。

## 3. 技术方案

### 3.1 数据流

```
用户提问
  → 模型调用 inspect（可选 selector / text / include_hidden / limit / frame_id）
  → 后台定位当前活动标签页并校验 http(s)
  → chrome.scripting.executeScript 注入 collectInteractiveElements
  → 页面内只读扫描，返回 InspectSnapshot
  → 格式化成模型可读文本 + UI 摘要
  → 模型继续回答或决定下一步
```

页面侧函数不依赖模块变量，因为它会被序列化后注入页面执行。所有辅助函数都定义在函数体内。

### 3.2 页面侧采集：只读边界

- **不点击、不聚焦、不滚动、不修改 DOM**。会读 `getComputedStyle`、`getBoundingClientRect` 和 `document.elementFromPoint`，这三个都是只读 API。
- **不写 data 属性、不挂全局变量、不加内容脚本**。编号只在本次结果里有效，跨调用不依赖页面内持久状态。
- **密码框和隐藏输入框直接从候选集合排除**（`input[type=password]`、`input[type=hidden]`），既不读取也不展示。
- **文本框当前值最多 80 字**，名称最多 80 字，可见文字最多 120 字，避免把整页内容塞进上下文。
- **候选上限 400 个**，防止极端页面拖垮注入调用；超出时标记截断。

候选集合的 CSS 选择器覆盖：链接、按钮、输入框、下拉框、文本域、`summary`、`contenteditable`、常见 ARIA 角色控件（button/link/menuitem/tab/checkbox/radio/switch/option/combobox/textbox/searchbox/slider）和可聚焦元素。

### 3.3 每个元素返回什么

| 字段 | 含义 |
| --- | --- |
| `ref` | 本次结果内的编号（`e1`、`e2`…），按文档顺序分配 |
| `selector` | 绝对 CSS 选择器；有 id 用 id，否则拼 `nth-of-type` 路径 |
| `tag` / `role` | 元素本身和它的语义角色 |
| `label` | 名称，优先级：`aria-labelledby` → `aria-label` → `label[for]` → 包裹的 label → `placeholder` → `alt` → `title` → 可见文字 |
| `text` | 按钮、链接等元素的可见文字 |
| `value` | 输入框/文本域/下拉框的当前值（密码框不读取） |
| `state` | 已勾选、已选中、已禁用、只读、已展开、已按下、当前焦点 |
| `visible` + `hidden_reason` | 是否可见；不可见时给出原因 |
| `pointer_events_none` | 看得见但鼠标穿透，点不中 |
| `covered` / `covered_by` | 元素中心被别的元素盖住，以及盖住它的是谁 |
| `in_viewport` | 是否在当前视口内 |
| `rect` | 视口坐标和尺寸 |

不可见原因固定为六种：`display_none`、`visibility_hidden`、`opacity_zero`、`near_transparent`（可能正在动画）、`zero_size`、`ancestor_hidden`。这样模型能针对原因决定下一步，而不是只看到「不可见」。

### 3.4 编号协议

- `ref` 按「通过 selector / text 筛选后的候选集合」的文档顺序分配，**不可见元素也占号**。
- 默认过滤不可见元素后，编号可能出现空档（例如只返回 `e2`、`e4`）。这是有意的：编号对应完整候选集合，后续写操作工具可以按同一集合重新解析，不会因为过滤条件变化而错位。
- `ref` 只在当前页面状态有效。页面跳转、列表刷新、弹窗打开后必须重新 `inspect`；工具描述和提示词都明确写了这一点。
- 当前版本只消费编号做展示和回答；写操作工具会复用同一份采集函数，按编号重新定位，并校验元素指纹后再执行。

### 3.5 技术选型

| 选择 | 理由 |
| --- | --- |
| `chrome.scripting.executeScript` 注入自包含函数 | 项目现有模式；不需要常驻内容脚本，Service Worker 重启后仍可工作 |
| TypeBox 定义参数 | 与现有工具一致，由模型 API 的 tool call 协议保证格式 |
| 纯 DOM 读取，不写属性 | 符合「页面快照只读」约束；避免污染页面和触发页面自己的 MutationObserver |
| `getComputedStyle` + 祖先链判断可见性 | 能区分「自己没有布局」「被祖先藏起来」「接近透明」等不同原因 |
| `elementFromPoint` 做遮挡检测 | 只读且便宜；每个可见元素一次命中测试 |
| Happy DOM 写单测 | 项目已有测试环境；布局用 `getBoundingClientRect` 桩替代 |
| 无新增依赖 | 全部能力基于浏览器标准 API |

### 3.6 安全边界

- 只接受当前活动标签页，不检查后台标签页，因此不需要授权门禁。
- 非 http/https 页面（`chrome://`、扩展商店、本地文件）直接返回可行动的错误。
- 选择器写错返回明确的语法错误；选择器找不到返回「没有找到指定区域」，不伪装成「页面没有元素」。
- 页面里的文字只作为资料展示，不执行页面里的任何指令。

## 4. 前端表现

**有，但很克制**：没有专属面板，复用现有工具步骤卡。

- 聊天时间线出现一张「检查页面元素」卡片，带鼠标指针图标、执行中/完成/失败状态和耗时。
- 摘要行显示 `找到 12 个可操作元素 · 2 个不可见 · 1 个被遮挡`。
- 展开「查看详情」后显示 JSON：页面标题、地址、总数、隐藏数、遮挡数、是否截断，以及最多 20 个元素的精简列表（编号、角色、名称、可见、遮挡）。上限 20 是为了避免会话落盘膨胀。
- 不渲染元素高亮，也不改变页面。用户看到的是 Agent「检查了什么」，不是页面被标注。

## 5. 用户场景

1. **填表前找字段**：用户说「帮我把这个表填了」，模型先 `inspect` 找出邮箱、电话、验证码字段及当前值；密码框不会出现在结果里。
2. **按文字定位按钮**：用户说「点第二个商品的加入购物车」，模型传 `text="加入购物车"`，拿到三个编号后按顺序选第二个。
3. **诊断点不动**：用户问「这个按钮为什么点不了」，模型传 `include_hidden=true`，看到「被祖先隐藏」「鼠标穿透」「被登录弹窗遮罩盖住」等具体原因。
4. **只看弹窗**：用户说「同意这个弹窗」，模型传 `selector="#modal"`，只列出弹窗内的按钮，不把整页按钮都塞进上下文。
5. **排查隐藏菜单**：用户说「退出登录在哪」，默认结果没有，模型开启 `include_hidden` 后发现菜单被 `display:none` 隐藏，给出「先展开菜单」的建议。

## 6. 测试

测试按类别分目录，放在 `tests/tools/inspect/`：

```
tests/tools/inspect/
  support.ts            # DOM 挂载、布局桩、遮挡桩
  collect.test.ts       # 采集与编号：元素类型、名称优先级、过滤、范围、截断
  visibility.test.ts    # 可见性：六种隐藏原因、鼠标穿透、遮挡、视口
  format.test.ts        # 模型文本与 UI 详情：计数、原因、空态、截断
  scenarios.test.ts     # 用户场景：登录表单、商品列表、点不动、弹窗、隐藏菜单
```

覆盖的关键行为：

- 密码框和隐藏输入框不出现在结果里。
- `aria-label` > `label` > `placeholder` > 文字的名称优先级。
- `text` 过滤不区分大小写；`selector` 只检查指定区域。
- 非法选择器与「找不到」区分开。
- 不可见元素默认不返回，但占用编号。
- 六种隐藏原因、鼠标穿透、遮挡来源、视口外标记。
- UI 详情最多 20 条。
- 模型文本包含密码框说明和编号失效提醒。

运行：`pnpm exec vitest run tests/tools/inspect`。

## 8. 已知边界与下一步

- **只检查当前活动标签页**。后台标签页需要等写操作版本一起加 `tab_id` 和授权门禁。
- **只检查顶层框架或指定 `frame_id`**，不自动遍历所有子框架。
- **不穿透 Shadow DOM**。对大量使用 Web Components 的页面，结果可能偏少；后续可加开放 Shadow Root 的递归采集。
- **遮挡检测基于元素中心点**，对异形元素可能误判；这是可接受的启发式。
- **编号不跨页面持久**。写操作版本需要复用同一采集函数，在点击前重新解析编号并校验选择器/名称，不一致时要求重新 `inspect`。
- 下一步：`click` / `fill` / `scroll` 合成一个 `act` 工具，按 `ref` 操作，全部注册权限门禁，并在每次操作后回读页面确认结果。
