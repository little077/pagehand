# read_page / read_tab 设计说明

这份文档记录当前读取链路的取舍，以及**还没做、但将来要补**的能力。改这两个工具之前先读完，避免把已经想清楚的边界又推倒重来。

## 1. 当前能力

两个工具共用 `lib/page/reader.ts` 的一套抽取管线，只是入口不同：

| 工具 | 读哪个页面 | 是否要授权 |
| --- | --- | --- |
| `read_page` | 当前活动标签页 | 不要 |
| `read_tab` | 指定 `tab_id` | 读非活动标签页时，由 `lib/agent/permission-gate.ts` 拦截并征求同意 |

共同参数：

| 参数 | 作用 | 默认 |
| --- | --- | --- |
| `mode` | `markdown` 整页转 Markdown；`article` 阅读模式抽正文；`text` 纯文本；`html` 清洗后的源码 | `markdown` |
| `selector` | 只读匹配 CSS 选择器的区域 | 整页 |
| `max_length` | 返回内容的最大字符数，1000～100000 | 12000 |
| `frame_id` | 读哪个子框架 | 0（顶层） |

### 为什么默认是 Markdown

Markdown 保留了标题层级、链接和图片，模型不用再单独拿一份“标题结构 + 链接列表”。链接和图片地址在页面注入阶段就换成了绝对地址，模型可以直接引用。内联的 `data:` / `blob:` 图片会被替换成 `[图片：alt]` 文本，避免 base64 把输出额度吃光。同一路径同时出现裸链接和带查询参数的链接时，Markdown 优先采用带参数的完整 URL；裸路径可能缺少运行时 token。

### 模式怎么选

代码只自动判断一件事：URL 以 `.pdf` 结尾时直接拒绝，让模型如实告诉用户当前读不了，不要反复重试。其余模式由模型根据工具描述和系统提示词选择：

- 长文 / 新闻 / 博客 / 文档 → `article`
- 表格、列表、搜索结果、普通页面 → `markdown`
- 只要文字、页面结构太乱 → `text`
- 反复读不到内容 → `html` 排查

没有做页面类型自动分类：同一个商品页既可能是长文也可能是列表，而模型手里有用户的具体问题，让它显式选更准，出问题时日志里也能看到选了什么。

### 子框架发现

`frame_id` 单独存在的原因是：iframe 是独立文档，顶层 `document.body` 里没有它的内容。默认只注入顶层，所以“页面看起来是空的”经常是内容在 iframe 里。

当前没有单独的 `list_frames` 工具。做法是：顶层抽取完成后，如果页面可见文字少于 400 字，就往所有框架注入一个只返回 `{标题, URL, 正文字数}` 的小函数，把有内容的子框架列在结果末尾，让模型带 `frame_id` 再读一次。这样少一个工具、少一份提示词和授权面。

注意：`frame_id` 由浏览器按标签页分配，页面刷新或跳转后会变，不能跨页面复用。

### 上下文预算

- 工具内按字符截断，默认 12000，上限 100000。
- 被截断时结果末尾会写明原文长度，并明确要求“一次调大 `max_length` 重读，不要循环拼接”。
- Pagehand **没有会话级压缩**，模型窗口固定按 128k 处理，单轮最多 8 个回合（debug 模式 200）。所以 `max_length` 是唯一护栏：一次读 10 万字会挤占后续所有轮次的空间，默认值不要随手调大。

## 2. 没做：outputPath

`outputPath` 的作用是把完整抽取结果写进虚拟文件系统，只给模型回一个路径和 1KB 预览，让正文完全不进上下文。现在**做不了**，缺的不是一个参数，而是三块基础设施：

1. **存储层**：Pagehand 没有文件系统。`chrome.storage.local` 默认只有 10MB，不适合大文件；`chrome.downloads` 会在用户下载目录产生可见文件，是另一类需要征求同意的能力；IndexedDB 能存，但目前只用来放会话，没有“按路径读写任意文件”的接口。
2. **读回工具**：模型拿到路径后必须能按需分段读回内容，否则这个路径对它是死字符串。需要类似 `read_file(path, offset, length)` 的只读工具，并接进工具白名单。
3. **路径规则**：目录约定、覆盖策略、大小上限、清理时机、导出给用户的入口，这些都没有定义。

### 补完之后再做 outputPath 的验收标准

- 能写入、能按偏移读回、能删除；单文件上限明确，超限有可行动的错误。
- 模型拿到的返回是“路径 + 字节数 + 1KB 预览”，不是正文。
- `max_length` 在设置 `outputPath` 时明确失效，且描述里写清楚原因。
- 有测试覆盖：大文件写入、分段读回、路径不存在、覆盖已有文件。
- 权限清单的变化单独评审，不和工具改动混在一起。

**在这个前提下，先不要给 read_page 加 outputPath 参数。** 加了也只能假装写盘，反而误导模型。

## 3. 没做：outline 与遮挡检测

`outline` 输出的是页面区域、选择器、坐标、可交互元素数量，还会检测挡在前面的弹窗和 cookie 条。它服务的是“看清楚再点”，不是“回答页面写了什么”。

Pagehand 当前没有任何写操作，点击被遮挡、按钮找不到这类失败还不存在，所以先不做。等接入点击 / 填表时再回来加，届时它应该和写工具的验收一起设计。

## 4. 实现约束（改代码前必须遵守）

- 注入到页面的函数必须是自包含的：`chrome.scripting.executeScript` 会把它序列化，不能引用模块级变量、常量或导入。
- 扩展后台（Service Worker）没有 DOM。HTML 转 Markdown 必须走 `entrypoints/offscreen/` 的离屏文档：`lib/page/offscreen.ts` 负责创建和发消息，`offscreen-protocol.ts` 是唯一的消息契约。
- 页面文本是不可信输入。当前 read_page 的结果还没有做提示词注入清洗，这是已知缺口；将来要加，必须只处理页面来源的字符串，不能动用户输入。
- 只读工具用 `replay: 'safe'`；`read_tab` 的门禁只注册在 `TOOL_GATES` 里，门禁本体不改。
- 不复制任何 AGPL 项目（如同类开源产品）的代码；可以借鉴能力清单和产品思路，实现必须自己写。

## 5. 已知缺口

- 提示词注入只做了边界标记和系统规则（“网页原文不可信”），没有剥离页面里的伪造标签或内容清洗；更隐蔽的注入仍可能生效。
- 工具内不预估 token：`max_length` 是字符数，窗口固定 128k 且没有压缩兜底，超长读取只能靠这个上限挡。
- 没有对注入的 HTML 体积设上限：超大页面会整份送到离屏文档，转换超过 20 秒就报错，并提示改用 selector 或 text。
- 没有分段读取：被截断只能调大上限重读，读完整本长文仍然依赖将来的 outputPath。
- 子框架只读一层：`frame_id` 指向的框架里如果还有嵌套 iframe，需要再发现一次；当前没有递归探测。
